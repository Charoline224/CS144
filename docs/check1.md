# 0 概述

在检查点 0 中，你使用了一个*互联网流套接字（Internet stream socket）*，通过 Linux 内置的传输控制协议（TCP）实现，从网站获取信息并发送电子邮件。尽管底层网络只提供“尽力而为”的数据报服务——也就是说，短数据包可能丢失、乱序、被修改或重复——这个 TCP 实现仍然能够产生一对*可靠且按序传输的字节流*：一条从你传向服务器，另一条从服务器传向你。你还在一台计算机的内存中亲自实现了字节流抽象。在接下来的几周中，你将自己实现 TCP，从而在由不可靠数据报网络分隔的两台计算机之间提供字节流抽象。

*⋆为什么要做这些？* 在一种不太可靠的服务之上提供另一种服务或抽象，是网络领域许多有趣问题的来源。在过去 40 年里，研究人员和实践者已经研究出如何通过互联网传输各种内容，包括消息和电子邮件、超链接文档、搜索引擎、声音和视频、虚拟世界、协作式文件共享以及数字货币。TCP 本身使用不可靠的数据报来提供一对可靠字节流，就是其中一个经典例子。可以合理地说，TCP 实现属于全球使用最广泛的复杂计算机程序之一。

这些实验作业会要求你以模块化方式逐步构建 TCP 实现。还记得你在检查点 0 中刚刚实现的 `ByteStream` 吗？在接下来的实验中，你最终会让两个 `ByteStream` 通过网络传输：一个是“出站” `ByteStream`，用于本地应用程序向套接字写入数据，而你的 TCP 会将这些数据发送*给*对端；另一个是“入站” `ByteStream`，用于保存来自*对端*、供本地应用程序读取的数据。

本检查点包含一个“动手实践”部分和一个实现部分。你可能希望在实验课前先开始实现部分，并在实验课上完成动手实践部分。如果你是 CGOE 学生，请使用 EdStem 与另一名学生协调完成动手实践部分的时间。

动手实践部分涉及多个相互配合的环节，因此可能会出现一些问题。实验课期间请耐心等待，我们会尽力让所有人的环境都能正常工作。如果你在 [https://cs144.net](https://cs144.net) 网站上看到错误消息，请在 EdStem 上发帖公开报告，我们会进行检查。

# 3 实现部分：将子串按顺序拼接

作为 CS144 实验的一部分，你将实现一个 TCP 接收器：它接收数据报，并将其转换为可靠的字节流，供应用程序读取。这与检查点 0 中你的 `webget` 程序从 Web 服务器读取字节流的方式类似。

TCP 发送方会把字节流切分成较短的“段”（每段子串不超过大约 1,460 字节），以便它们能够装入一个数据报。但是，网络可能会将这些数据报重新排序、丢弃，或者多次传递同一个数据报。接收方必须重新组装这些段，还原它们最初对应的连续字节流。

*在本检查点中*，你要创建负责这种重组的模块：`Reassembler`。它会接收一些子串，每个子串由一段字节组成，并且包含这段字节在完整字节流中的起始索引。字节流中的每个字节都有唯一的索引，从 0 开始递增。只要 `Reassembler` 知道字节流中的下一个字节，就应当将该字节写入 `ByteStream` 的 `Writer` 端——这就是你在检查点 0 中实现的同一个 `ByteStream`。`Reassembler` 的“客户”可以从 `Reader` 端读取数据。

### 接口如下：

```cpp
// 将一个新的子串插入 ByteStream，以便进行重组。
void insert(uint64_t first_index, std::string data, bool is_last_substring);

// Reassembler 本身存储了多少字节？
// 此函数仅用于测试；不要为了实现它而增加额外状态。
uint64_t count_bytes_pending() const;

// 访问输出流的 reader。
Reader& reader();
```

*⋆为什么要做这个？* TCP 能够抵抗乱序和重复传输，正是因为它能够将字节流中任意位置的片段重新拼接成原始字节流。将这一功能实现为一个独立且可测试的模块，会让后续工作更加容易。

完整的 `Reassembler` 公共接口定义在 `reassembler.hh` 头文件中。你的任务是实现这个类。你可以根据需要为 `Reassembler` 类增加任意私有成员和成员函数，但不能修改其公共接口。

## 3.1 Reassembler 内部应当存储什么？

`insert` 方法会告诉 `Reassembler` 一个新的 `ByteStream` 片段，以及该片段在整体字节流中的位置，也就是子串起始位置的索引。

原则上，`Reassembler` 需要处理三类信息：

1. **已经成为字节流下一个字节的字节。** `Reassembler` 一旦知道这些字节，就应当立即将它们推送到流中，即输出流的 `.writer()`。
2. **位于流当前可用容量范围内，但还不能写入的字节。** 之所以不能写入，是因为它们前面的某些字节仍然未知。这些字节应当暂存在 `Reassembler` 内部。
3. **超出流当前可用容量的字节。** 这些字节应当被丢弃。`Reassembler` 不应存储任何无法立即推送到 `ByteStream`、也无法在前面的字节变得已知后立即推送的字节。

这样做的目标是限制 `Reassembler` 和 `ByteStream` 使用的内存总量，而不论传入的子串以何种顺序到达。我们在配图中对此进行了说明。“容量”同时是下列两者的上限：

1. 重组后的 `ByteStream` 中缓存的字节数（图中以绿色表示）；
2. “尚未组装”的子串可以使用的字节数（图中以红色表示）。

在实现 `Reassembler` 并处理测试时，这张图可能会很有帮助——“正确”的行为并不总是直观的。

## 3.2 常见问题

- **整个字节流的第一个字节的索引是多少？**

  是 0。

- **实现应该有多高效？**

  数据结构的选择同样很重要。请不要把这项作业当成构建极其低效的空间或时间数据结构的挑战——`Reassembler` 将成为你 TCP 实现的基础。你有很多选择。我们提供了一个基准测试；只要速度超过 `0.1 Gbit/s`（100 兆比特每秒）即可接受。顶级的 `Reassembler` 可以达到 `10 Gbit/s`。

- **应当如何处理不一致的子串？**

  你可以假设不存在这种情况。也就是说，你可以假设存在一个唯一的底层字节流，并且所有子串都是它的准确切片。

- **可以使用哪些内容？**

  你可以使用标准库中的任何部分。特别是，我们希望你至少使用一种数据结构。

- **什么时候应当把字节写入流？**

  应当尽快写入。唯一一种字节不应当出现在流中的情况，是它前面还有某个字节尚未被“推送”进流中。

- **传递给 `insert()` 函数的子串可以重叠吗？**

  可以。

- **是否需要为 `Reassembler` 增加私有成员？**

  需要。子串可能以任意顺序到达，因此你的数据结构必须“记住”这些子串，直到它们可以被放入流中——也就是直到它们之前的所有索引都已经被写入。

- **重组数据结构可以存储重叠的子串吗？**

  不可以。确实可以实现一个“接口正确”的 `Reassembler`，让它存储相互重叠的子串。但这样做会破坏“容量”作为内存上限的意义。如果调用方提供了关于同一个索引的重复信息，`Reassembler` 应当只存储该信息的一份副本。

- **`Reassembler` 会使用 `ByteStream` 的 `Reader` 端吗？**

  不会——`Reader` 端供外部客户使用。`Reassembler` 只使用 `Writer` 端。

- **期望代码有多少行？**

  在起始代码上运行 `./scripts/lines-of-code` 时，输出如下：

  ```text
  ByteStream: 90 lines of code
  Reassembler: 26 lines of code
  ```

  在我们的解决方案上运行时，输出如下：

  ```text
  ByteStream: 109 lines of code
  Reassembler: 87 lines of code
  ```

  因此，在起始代码的基础上，`Reassembler` 的合理实现规模大约是 50～60 行。

- **更多常见问题：**

  请参阅 [https://cs144.github.io/lab](https://cs144.github.io/lab) 上的 `faq.html`。
