## 2 检查点 3：TCP 发送方

TCP 是一种协议，它通过不可靠的数据报，可靠地传输一对流量受控的字节流（每个方向各有一个）。两个参与者共同构成 TCP 连接，并且每一方都是另一方的对端。每个对端同时承担两种角色：既是自己输出字节流的“发送方”，也是输入字节流的“接收方”。

本周，你将实现 TCP 的“发送方”部分。它负责从某个发送端应用创建并写入的 `ByteStream` 中读取数据，并将该字节流转换为一系列待发送的 TCP 报文段。在远端，TCP 接收方会把这些报文段（那些成功到达的报文段——它们不一定全部到达）还原为原始字节流，并向发送方返回确认和窗口通告。

`TCPSender` 需要负责：

- 跟踪接收方的窗口（接收带有确认号和窗口大小的 `TCPReceiverMessage`）；
- 在可能的情况下填满窗口：从 `ByteStream` 中读取数据，创建新的 TCP 报文段（必要时包括 `SYN` 和 `FIN` 标志），并发送这些报文段。发送方应当持续发送，直到窗口已满，或者输出 `ByteStream` 中没有更多数据可发送；
- 跟踪已经发送但尚未被接收方确认的报文段——这些报文段称为“未确认报文段”（outstanding segments）；
- 如果经过了足够长的时间而报文段仍未被确认，则重新发送未确认报文段。

> **为什么要做这些？**
>
> 基本原则是：发送接收方允许发送的所有数据（即填满窗口），并持续重传，直到接收方确认每个报文段。这称为“自动重传请求”（Automatic Repeat reQuest，ARQ）。发送方把字节流划分成多个报文段，并在接收方窗口允许的范围内尽可能多地发送它们。
>
> 得益于你上周的工作，我们知道，只要远端 TCP 接收方至少收到每个带有索引标记的字节一次，就能够重建字节流，而不必关心这些字节到达的顺序。发送方的任务，就是确保接收方至少收到每个字节一次。

> **注 1：**必须记住，接收方可以是任何符合 TCP 标准的有效 TCP 接收方，并不一定是你自己实现的 `TCPReceiver`。互联网标准的一个重要价值，就是为原本可能行为完全不同的端点建立一种共同语言。

### 2.1 `TCPSender` 如何知道报文段是否丢失？

你的 `TCPSender` 将发送许多 `TCPSenderMessage`。每个消息都包含输出 `ByteStream` 中的一个子串（该子串也可能为空），并带有序列号，以表示它在字节流中的位置；字节流的开头会标记 `SYN` 标志，结尾会标记 `FIN` 标志。

除了发送这些报文段之外，`TCPSender` 还必须跟踪未确认报文段，直到它们所占据的序列号全部得到确认。`TCPSender` 的所有者会周期性调用 `TCPSender` 的 `tick` 方法，表示时间正在流逝。`TCPSender` 必须检查其未确认 `TCPSenderMessage` 集合，并判断最早发送的报文段是否已经在没有得到确认的情况下持续了太长时间（也就是说，它所占据的**所有**序列号都尚未被确认）。如果是，就需要再次发送该报文段。

下面是“持续太长时间”的具体规则。你将实现这部分逻辑，它有些细节，但我们不希望你担心隐藏测试会故意刁难你，也不希望你把它当成 SAT 考试中的文字题。我们会在本周提供合理的单元测试；当你完成整个 TCP 实现后，实验 4 中还会提供更加完整的集成测试。只要你 100% 通过这些测试，并且实现是合理的，就没有问题。

> **为什么要做这些？**
>
> 总体目标是让发送方及时检测到报文段丢失，并在需要时重新发送。等待多久再重传非常重要：你不希望发送方等待太久，因为这会延迟数据流向接收应用；但你也不希望它过早重传一个本来只要再等一会儿就会被确认的报文段，因为那会浪费互联网宝贵的传输容量。

1. `TCPSender` 的 `tick` 方法每隔几毫秒会被调用一次，并接收一个参数，表示自上次调用该方法以来经过了多少毫秒。使用这个参数维护一个概念上的“`TCPSender` 已经运行的总毫秒数”。请不要尝试调用操作系统或 CPU 提供的任何“时间”或“时钟”函数——`tick` 方法是你获取时间流逝信息的**唯一途径**。这样可以保证实现具有确定性并且易于测试。

2. 构造 `TCPSender` 时，会传入一个参数，表示重传超时时间（Retransmission Timeout，`RTO`）的“初始值”。`RTO` 是在重新发送一个未确认 TCP 报文段之前需要等待的毫秒数。`RTO` 的值会随时间变化，但“初始值”保持不变。起始代码会把 `RTO` 的“初始值”保存到一个名为 `initial_RTO_ms` 的成员变量中。

> **注 2：**这些规则基于 TCP“真实”规则的简化版本，即 RFC 6298 中的建议 5.1 至 5.6。这里的版本有所简化，但你的 TCP 实现仍然能够与互联网上的真实服务器通信。

3. 你需要实现重传计时器：这是一个可以在某个时刻启动的闹钟，经过 `RTO` 时间后闹钟响起（或称“到期”）。需要强调的是，这里的时间流逝来自对 `tick` 方法的调用，而不是通过获取实际的当前时间。

4. 每当发送一个包含数据的报文段（即在序列空间中长度非零的报文段）时，无论这是第一次发送还是重传，如果计时器当前没有运行，就启动计时器，使其在当前 `RTO` 毫秒后到期。所谓“到期”，是指在未来某个经过指定毫秒数的时刻时间耗尽。

5. 当所有未确认数据都已经得到确认时，停止重传计时器。

6. 如果调用 `tick` 时重传计时器已经到期：

   **(a)** 重新发送尚未被 TCP 接收方完全确认的最早报文段（序列号最低的报文段）。你需要将未确认报文段存储在某种内部数据结构中，使得能够执行这一操作。

   **(b)** 如果窗口大小不为零：

   **i.** 跟踪“连续重传”的次数，并将其加一，因为你刚刚进行了重传。你的 `TCPConnection` 将使用这个信息判断连接是否已经无望（连续重传次数过多），并决定是否需要中止连接。

   **ii.** 将 `RTO` 的值加倍。这称为“指数退避”（exponential backoff），可以在网络状况不佳时减慢重传速度，以避免进一步加剧网络拥塞。

   **(c)** 重置重传计时器，并重新启动它，使其在 `RTO` 毫秒后到期（如果刚刚将 `RTO` 加倍，则应使用加倍后的值）。

7. 当接收方发送一个确认号，确认收到了新的数据时（该确认号反映的绝对序列号大于此前收到的任何确认号）：

   **(a)** 将 `RTO` 恢复为其“初始值”。

   **(b)** 如果发送方仍有未确认数据，则使用当前 `RTO` 的值重新启动重传计时器，使其在该时间后到期。

   **(c)** 将“连续重传”计数重置为零。

你可以选择把重传计时器的功能实现为一个独立的类，但这不是强制要求。如果这样做，请将该类加入现有文件（`tcp_sender.hh` 和 `tcp_sender.cc`）中。

### 2.2 实现 TCP 发送方

好了！我们已经讨论了 TCP 发送方的基本工作原理：从输出字节流中读取数据，将其拆分为报文段并发送；如果报文段没有及时得到确认，就持续重新发送。我们也讨论了何时应当判断某个未确认报文段已经丢失，并需要重传。

现在开始讨论 `TCPSender` 要提供的具体接口。它需要处理四个重要事件：

#### 1. `void push(const TransmitFunction& transmit);`

系统要求 `TCPSender` 从输出字节流中“填充窗口”：它从字节流中读取数据，并尽可能多地发送 `TCPSenderMessage`，但前提是**仍有新字节可读取，并且窗口中还有可用空间**。发送时，需要对每个消息调用传入的 `transmit()` 函数。

你需要确保发送的每个 `TCPSenderMessage` 都完整地位于接收方窗口之内。每个独立消息都应尽可能大，但不得超过 `TCPConfig::MAX_PAYLOAD_SIZE` 指定的值。

你可以使用 `TCPSenderMessage::sequence_length()` 方法计算一个报文段占用的序列号总数。请记住，`SYN` 和 `FIN` 标志也各自占用一个序列号，因此它们也会占用窗口空间。

> **如果窗口大小为零，应该怎么办？**
>
> 如果接收方通告的窗口大小为零，`push` 方法应当暂时把窗口大小当作一。发送方可能会因此发送一个字节，而该字节会被接收方拒绝并且不会得到确认；但这也可能促使接收方发送一个新的确认报文段，从而告知发送方窗口中已经出现了更多空间。如果不这样做，发送方将永远不知道自己何时又可以开始发送。

这是实现中针对零窗口情况唯一应该采取的特殊行为。`TCPSender` 不应真正记住一个虚假的窗口大小一；这个特殊处理只应存在于 `push` 方法内部。

另外需要注意：即使窗口大小是一（或者是 20、200），窗口也可能已经被填满。“窗口已满”与“窗口大小为零”不是同一回事。

#### 2. `void receive(const TCPReceiverMessage& msg);`

发送方会从接收方收到一条消息，其中包含窗口新的左边界（即 `ackno`）和右边界（即 `ackno + window size`）。`TCPSender` 应检查自己的未确认报文段集合，并删除那些现在已经被完全确认的报文段（也就是：确认号大于该报文段所占据的全部序列号）。

#### 3. `void tick(uint64_t ms_since_last_tick, const TransmitFunction& transmit);`

时间已经过去了——自上一次调用该方法以来经过了指定数量的毫秒。发送方可能需要重传某个未确认报文段；此时可以调用 `transmit()` 函数进行重传。

提醒：请不要在代码中使用真实世界的“时钟”或 `gettimeofday` 等函数；时间流逝的唯一依据是 `ms_since_last_tick` 参数。

#### 4. `TCPSenderMessage make_empty_message() const;`

`TCPSender` 应生成并发送一个长度为零、序列号设置正确的消息。当对端希望发送一个 `TCPReceiverMessage`（例如，因为它需要确认来自对端发送方的数据），同时又需要生成一个配套的 `TCPSenderMessage` 时，这一功能会很有用。

注意：像这种不占用任何序列号的报文段，不需要作为“未确认报文段”进行跟踪，也不会被重传。

要完成检查点 3，请查看 `src/tcp_sender.hh` 中的完整接口，并在 `tcp_sender.hh` 和 `tcp_sender.cc` 文件中实现完整的 `TCPSender` 公有接口。我们预计你会添加一些私有方法和成员变量，也可能会添加一个辅助类。

### 2.3 常见问题与特殊情况

- **在 `receive` 方法告知发送方之前，`TCPSender` 应假设接收方窗口大小是多少？**

  一。

- **如果一个确认只确认了某个未确认报文段的一部分，应该怎么办？是否应当把已经确认的字节从报文段中裁剪掉？**

  TCP 发送方当然可以这样做，但对于本课程而言，没有必要实现得这么复杂。在一个报文段被完全确认之前，都把它视为完整的未确认报文段——也就是说，只有当它所占据的所有序列号都小于 `ackno` 时，才认为它已经被完全确认。

- **如果我发送了三个独立的报文段，内容分别为 “a”、“b” 和 “c”，而它们从未得到确认，那么之后能否把它们合并为一个包含 “abc” 的大报文段再重传？还是必须分别重传每个报文段？**

  TCP 发送方当然可以这样做，但对于本课程而言，同样没有必要实现得这么复杂。只需分别跟踪每个未确认报文段，当重传计时器到期时，重新发送最早的未确认报文段即可。

- **是否应该将空报文段存储在“未确认报文段”数据结构中，并在需要时重传？**

  不应该。只有那些传递了数据、也就是在序列空间中占用一定长度的报文段，才应被作为未确认报文段跟踪并可能被重传。一个不占用任何序列号的报文段（没有 `SYN`、有效载荷或 `FIN`）不需要被记住，也不需要被重传。

#### 4.1.1 让 Linux 的 TCP 与自身通信

  ```bash

  ```

- 如果一切正常，“服务器”会输出类似下面的内容：

  ```text
  DEBUG: New connection from 169.254.144.1:36568
  ```

  “客户端”会输出类似下面的内容：

  ```text
  DEBUG: Connecting to 169.254.144.1:9090...
  DEBUG: Successfully connected to 169.254.144.1:9090.
  ```

  ```text

  ```

  注意，另一端仍然可以继续向已经关闭的对端发送数据——两个方向的数据流可以独立关闭，一个方向关闭并不会阻止另一个方向继续传输。

- 现在，在另一个终端中输入 `Ctrl-D`，结束第二个方向的数据流。如果一切正常，两个程序都会退出，并在两个终端中返回命令行。这表示 TCP 连接在两个方向上都已经结束（正如课堂中讨论的那样，Linux 会在后台“保持”一段时间，然后才重新使用某个端口号，以降低“两将军问题”的可能性）。

#### 4.1.2 让你的 TCP 与 Linux 的 TCP 通信

重复上面的步骤，但这次让你自己的 TCP 实现与 Linux 的 TCP 连接。首先运行：

```bash
sudo ./scripts/tun.sh start 144
```

该命令会允许你的实现发送原始互联网数据报，而不需要以 root 身份运行。每次重启虚拟机后，都需要重新运行此命令。

然后重新进行上面的实验，将其中一个程序（客户端或服务器）替换为 `tcp_ipv4`（也就是你自己的 TCP 实现）。连接是否仍能像之前一样建立？两个对端是否仍然可以互相输入，并在另一个对端的窗口中看到文字？如果可以，祝贺自己（我们也会向你表示祝贺）——你已经成功了！如果不行……就开始调试吧。你可以使用类似下面的命令捕获 TCP 报文段：

```bash
sudo rm -f /tmp/capture.raw
sudo tcpdump -n -w /tmp/capture.raw -i tun144 --print --packet-buffered
```

之后，可以像之前一样在 Wireshark 中查看生成的 `/tmp/capture.raw` 文件。

在两个方向都输入一些内容之后，尝试关闭其中一个 `ByteStream`，同时继续在另一个方向输入一些内容。两个数据流都通过 `Ctrl-D` 结束后，两个程序是否都能干净地退出？它们应该能够退出，不过你可能需要等待 `tcp_ipv4` 一段时间，以降低“两将军问题”的可能性。它什么时候需要等待——是在它第一个关闭数据流时，还是在它第二个关闭数据流时？这是否与课堂上的讨论一致？

#### 4.1.3 尝试通过“一兆字节挑战”

当你已经能够进行基本通信后，尝试在 `tcp_ipv4`（你的 TCP 实现）和 `tcp_native`（Linux TCP）之间传输文件。

要创建一个大小为 12345 字节的随机文件 `/tmp/big.txt`，运行：

```bash
dd if=/dev/urandom bs=12345 count=1 of=/tmp/big.txt
```

你可以选择传输方向，也就是由客户端发送文件，或者由服务器发送文件。

要让服务器在接受连接后立即发送文件，可以将标准输入重定向到该文件：

```bash
./build/apps/tcp_native -l 0 9090 < /tmp/big.txt
```

要让客户端接收文件，可以通过从 `/dev/null` 重定向来关闭其输出流，并将标准输出重定向到另一个文件 `/tmp/big-received.txt`：

```bash
</dev/null ./build/apps/tcp_ipv4 169.254.144.1 9090 > /tmp/big-received.txt
```

或者，让服务器接收文件：

```bash
./build/apps/tcp_native -l 0 9090 > /tmp/big-received.txt
```

让客户端发送文件：

```bash
./build/apps/tcp_ipv4 169.254.144.1 9090 < /tmp/big.txt
```

要比较两个文件并确保它们完全相同，可以运行：

```bash
sha256sum /tmp/big.txt
```

或者：

```bash
sha256sum /tmp/big-received.txt
```

如果 SHA-256 哈希值一致，你几乎可以确定文件传输正确。

请依次使用以下大小的文件进行测试：一个很小的文件（12 字节）、65534 字节（略小于 `2^16`）、65537 字节（略大于 `2^16`）、200000 字节，最后是完整的一兆字节（1000000 字节）。如果所有文件的哈希值都一致，再次祝贺自己！如果不一致，就需要调试，可能要使用上面介绍的 `tcpdump` 和 Wireshark。

### 4.3 再次处理 `webget`

还记得你在检查点 0 中编写的 `webget.cc` 吗？它使用的是 Linux 内核提供的 TCP 实现（`TCPSocket`）。现在，我们希望你将它切换为使用自己的 TCP 实现，同时不改变其他内容。我们认为你只需要做以下修改：

- 将：

  ```cpp
  #include "socket.hh"
  ```

  替换为：

  ```cpp
  #include "tcp_ip_socket.hh"
  ```

- 将 `TCPSocket` 类型替换为 `CS144TCPSocket`。

- 在 `get_url()` 函数末尾添加：

  ```cpp
  socket.wait_until_closed();
  ```

> **为什么要这样做？**
>
> 通常，即使用户进程已经退出，Linux 内核也会负责等待 TCP 连接完成“干净关闭”，并释放端口占用。但由于你的 TCP 实现完全运行在用户空间中，除了你的程序之外，没有其他组件会继续跟踪连接状态。因此，添加这次调用可以让套接字一直等待到连接完全关闭。

重新编译，并运行以下命令：

```bash

```
